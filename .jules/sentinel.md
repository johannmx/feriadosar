**Prevention:** Always explicitly configure secure headers (e.g., CSP, X-Frame-Options, X-Content-Type-Options) and disable `server_tokens` in NGINX container configurations.

## 2026-04-07 - [Harden CSP and Prevent Client-Side Race Condition]

In `App.tsx`, the `useEffect` hook handling the external API fetch lacked an abort cleanup function, which could cause a client-side race condition and resource exhaustion if the user rapidly toggled between years.
**Learning:** Even modern React apps (which don't need inline scripts in production) can inherit insecure default settings if not explicitly stripped out of custom NGINX configurations. **Prevention:** Always remove `'unsafe-inline'` from CSP `script-src` unless absolutely required and explicitly document why. Always return a cleanup function utilizing `AbortController.abort()` for any async requests executed inside `useEffect`.

## 2026-04-08 - [Add HSTS and Permissions-Policy Security Headers]
**Vulnerability:** The production NGINX configuration in `Dockerfile` was missing the `Strict-Transport-Security` (HSTS) and `Permissions-Policy` headers. Missing HSTS can expose users to Man-in-the-Middle (MitM) attacks during initial connection, while missing Permissions-Policy allows unauthorized or potentially malicious use of browser features like geolocation, camera, and microphone.

**Prevention:** Always enforce HSTS and define a strict Permissions-Policy in web server configurations to restrict unauthorized browser feature usage and ensure encrypted communication.

## 2026-04-09 - [Harden CSP object-src and Prevent Dynamic Fetch SSRF]

**Prevention:** Always strictly validate dynamic variables (e.g., bounds checking numbers) immediately before network interpolation. Explicitly set `object-src 'none'`, `base-uri 'none'`, and `upgrade-insecure-requests` in all CSP configurations.

## 2026-04-11 - [Fail Securely on Blocked LocalStorage]
**Vulnerability:** The `useTheme` hook directly accessed `localStorage` to read and persist the user's theme preference. If a user configured their browser to block third-party cookies or site data (e.g., strict privacy mode), accessing `localStorage` synchronously throws a `SecurityError`. Since these calls were outside a `try...catch` block, this unhandled exception would crash the entire React application on load (Client-side DoS).
**Learning:** Browser APIs that interact with storage or sensitive permissions can throw synchronous exceptions based on user privacy settings. A core security principle is to "fail securely"—the application should gracefully degrade to default behavior (e.g., using the default system theme) rather than failing catastrophically and denying service.
**Prevention:** Always wrap `localStorage` and `sessionStorage` operations (`getItem`, `setItem`, `removeItem`) in `try...catch` blocks. Ensure the fallback behavior maintains usability.
## 2026-04-14 - [Validate External API Content-Type]
**Vulnerability:** The `fetch` call to `https://api.argentinadatos.com` in `App.tsx` did not specify an `Accept` header or validate the `Content-Type` of the response before parsing it as JSON. **Learning:** Implicitly trusting the content type of external APIs is a defense-in-depth risk. Even if the payload format is validated later, attempting to parse an unexpected format (like HTML as JSON) can cause unhandled exceptions or crash the application.
**Prevention:** Always explicitly request expected formats (e.g., `Accept: application/json`) and strictly validate the `Content-Type` of responses (e.g., `res.headers.get('content-type')?.includes('application/json')`) before processing them.

## 2026-04-15 - [Fix NaN Bypass in Numeric Validation]
**Vulnerability:** The numeric validation for the `year` parameter in `src/App.tsx` used `typeof year !== 'number'`. This check is vulnerable to bypasses because in JavaScript, `NaN` and `Infinity` are technically of type `'number'`. If `year` was `NaN`, both `year < 2000` and `year > 2100` would evaluate to `false`, allowing the parameter to bypass the boundary checks completely.
**Learning:** Using `typeof x === 'number'` is insufficient for validating numbers when boundaries are involved, as `NaN` fails numerical comparisons (returning `false`) but passes the type check, which can lead to unexpected behavior or bypasses in validation logic.
**Prevention:** Always use `Number.isSafeInteger()` or `Number.isFinite()` when validating numeric input, especially when ensuring the value falls within specific boundaries, to prevent `NaN` and `Infinity` from bypassing checks.
