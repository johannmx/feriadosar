## 2026-03-25 - [Add Timeout and Error Sanitization to External API Call]
**Vulnerability:** The `fetch` call to `https://api.argentinadatos.com` in `App.tsx` had no timeout configuration, meaning the application could hang or suffer resource exhaustion if the external API responds very slowly or indefinitely. Additionally, raw error objects were being passed to `console.error()`, which can leak internal stack traces or details to the browser console. Finally, the project had an outdated dependency `brace-expansion` causing an audit warning.
**Learning:** External API integrations without timeout limits and unsanitized error logging are common medium-severity security and stability risks in frontend components. Fixing these provides better defense in depth.
**Prevention:** Always implement an `AbortController` and `setTimeout` alongside `fetch` calls, and avoid logging full error object details directly to the console in production environments.

## 2026-04-04 - [Add NGINX Security Headers in Production Dockerfile]
**Vulnerability:** The production `Dockerfile` configured an NGINX server without important HTTP security headers (like `X-Frame-Options`, `X-Content-Type-Options`, `Content-Security-Policy`, and `Referrer-Policy`) and leaked the NGINX version via the `Server` header. This could leave the application open to Clickjacking, MIME-type sniffing, XSS, and information disclosure attacks.
**Learning:** Containerized static websites often use basic NGINX configurations that default to insecure settings. Even purely static sites should enforce a strong Content Security Policy and basic anti-framing headers to follow defense-in-depth principles.
**Prevention:** Always explicitly configure secure headers (e.g., CSP, X-Frame-Options, X-Content-Type-Options) and disable `server_tokens` in NGINX container configurations.

## 2026-04-05 - [Strict Trust Boundary Validation for Local Storage and API Input]
**Vulnerability:** External APIs and client-side storage (`localStorage`) act as trust boundaries but were being consumed implicitly without validation. In `useTheme.ts`, untrusted localStorage data was cast directly and applied to `classList.add()`, which could trigger `DOMException` if injected with space-separated malicious strings. In `App.tsx`, the raw JSON array from the external API was mapped to the DOM without structure or length validation, posing a minor client-side DoS risk or unexpected behavior if the API output changed.
**Learning:** Implicit trust in external data sources (even APIs considered "official") or local storage allows data integrity issues to become execution or runtime exceptions. Validation at the trust boundary is a core pillar of defense-in-depth.
**Prevention:** Always validate format, length, and types when crossing a trust boundary, ensuring data conforms exactly to expected internal structures before it interacts with standard library functions like `classList.add()` or React state rendering.

## 2026-04-06 - [Add Strict Validation for External API Payload]
**Vulnerability:** The raw JSON array fetched from the external API (`https://api.argentinadatos.com`) was being implicitly trusted. While structural typing was present, string lengths were not bound and the `fecha` date string wasn't checked for parseability. An invalid date payload could lead to a `NaN` evaluation or exception within the `Date.toLocaleDateString()` component method, causing an unhandled React crash (client-side DoS).
**Learning:** Implicit trust in external API formats (even "official" ones) poses a stability risk, particularly when mapping data directly to Date object methods that throw errors on bad inputs. Length validation is also a crucial defense-in-depth tactic against payload tampering that causes rendering lag or memory exhaustion.
**Prevention:** Always validate external payloads rigorously. Check format, size, and ensure dates parse without producing `NaN` before rendering them into the UI state.

## 2026-04-07 - [Harden CSP and Prevent Client-Side Race Condition]
**Vulnerability:** The NGINX Content-Security-Policy header in the `Dockerfile` included `'unsafe-inline'` in the `script-src` directive, weakening defense against XSS. In `App.tsx`, the `useEffect` hook handling the external API fetch lacked an abort cleanup function, which could cause a client-side race condition and resource exhaustion if the user rapidly toggled between years.
**Learning:** Even modern React apps (which don't need inline scripts in production) can inherit insecure default settings if not explicitly stripped out of custom NGINX configurations. Also, external fetches within `useEffect` must always be cleanly aborted on dependency changes to prevent stale states from overwriting newer ones and exhausting client/server resources.
**Prevention:** Always remove `'unsafe-inline'` from CSP `script-src` unless absolutely required and explicitly document why. Always return a cleanup function utilizing `AbortController.abort()` for any async requests executed inside `useEffect`.

## 2026-04-08 - [Add HSTS and Permissions-Policy Security Headers]
**Vulnerability:** The production NGINX configuration in `Dockerfile` was missing the `Strict-Transport-Security` (HSTS) and `Permissions-Policy` headers. Missing HSTS can expose users to Man-in-the-Middle (MitM) attacks during initial connection, while missing Permissions-Policy allows unauthorized or potentially malicious use of browser features like geolocation, camera, and microphone.
**Learning:** Proper security headers form a crucial layer of defense for web applications. HSTS ensures that browsers only connect over HTTPS, preventing downgrade attacks. Permissions-Policy actively restricts the features available to the site, reducing the attack surface.
**Prevention:** Always enforce HSTS and define a strict Permissions-Policy in web server configurations to restrict unauthorized browser feature usage and ensure encrypted communication.
